# Implementation Spec — "Clean Conditions & Features" + Stat-Panel Toggle Fix

This spec covers THREE independent deliverables. They share no state and can be
implemented/merged separately:

  A. Conditions cleanup — categorize every condition buff/debuff and wire (or
     explicitly flag) its mechanical consequence.
  B. "Add Feature" button — let the user attach a real feat from the existing
     FEATS registry (not via ASI) and wire each feat's consequence.
  C. Fix the broken "toggle stats panel" button glyph.

Deliverable C is a one-character bugfix and is fully specified at the end; do it
first so it can ship independently.

NOTE on a doc-vs-code discrepancy you will hit: CLAUDE.md says AC lives in
`domain/rules/computeArmorClass`. In THIS codebase AC is actually computed by
`computeACFull` in `src/renderer/src/shared/data/charCalculations.ts`, and there is
NO pure `computeArmorClass` in `domain/rules`. Likewise saving-throw / skill /
attack-roll TOTALS are assembled inline in `features/abilities/AbilitiesPanel.tsx`
and `features/combat-actions/ActionDetailPanel.tsx`, using the small pure helpers
`savingThrowBonus`, `skillBonus`, `mod`, `computeSpeedFull` from `charCalculations`.
Follow the REAL layout below, not the idealized one in CLAUDE.md.

  (<=999px) renders garbage text `â˜°` instead of a hamburger icon.

`@media (max-width:999px)`), and the slide-in rules in
`widgets/character-view/CharacterView.module.css` (`.leftCol` /`.leftColOpen`
/`.drawerBackdrop`) are all CORRECT. Do NOT touch the CSS.

U+2630). Save the file as UTF-8 (no BOM). Verify afterward that the three bytes are

================================================================================
DELIVERABLE A — Conditions cleanup & wiring
================================================================================

## Problem Definition
- WHAT (user-facing): The Conditions panel currently lists 16 status conditions as
  plain toggle chips with NO mechanical effect, while spell "buffs" live in a
  SEPARATE picker backed by `activeBuffSpells` where only AC-setting (Mage Armor)
  and attack riders (Bless/Divine Favor/Hunter's Mark/Magic Weapon) actually do
  anything. The player cannot tell which conditions are buffs vs debuffs, and most
  carry no consequence. Goal: every condition is explicitly categorized
  buff/debuff/neutral and either (1) actually changes the computed stats it should,
  or (2) shows an explicit, player-readable FLAG describing the manual rule when the
  effect can't be auto-computed in a sheet (no targeting/combat engine exists).
- INPUTS read: `char.conditionIds: ActiveCondition[]`, `char.activeBuffSpells`,
  `char.armorClass`, `char.speed`, `char.abilityScores`, `char.concentrationSpellId`,
  and the spell registry (`SPELL_BY_ID`, `BUFF_CONDITION_SPELLS`).
- OUTPUTS: a typed CONDITIONS registry drives the panel; computable conditions feed
  the existing `computeACFull` / `computeSpeedFull` and the save/attack detail
  panels; non-computable ones render as a tag with an effect note. Persisted field
  that changes: `char.conditionIds` (already persisted; shape unchanged).
- CONSTRAINTS (5e RAW, cited per condition in the registry): offline-first; must run
  on Electron + iOS; must not break existing saves (legacy `conditionIds` entries
  already exist).

## Data Model
Existing (`src/renderer/src/entities/condition/types.ts`) — already defines but
NOBODY uses:
    ConditionCategory = 'debuff' | 'buff' | 'neutral'
    ConditionEffect    = { affects: 'ac'|'attack'|'saving-throw'|'speed'|'ability-check'|'other'; description }
    Condition          = { id; name; category; effects: ConditionEffect[]; description }

Extend `ConditionEffect` with an OPTIONAL machine-readable rider so the panel/rules
can distinguish "auto-computed" from "manual flag" without parsing prose. Add ONLY:
    // NEW (optional, back-compat): structured handle for the computable subset.
    mechanic?:
      | { kind: 'speedMultiplier'; value: number }          // e.g. 0.5 difficult terrain / slowed
      | { kind: 'acDelta';        value: number }            // e.g. -2 slowed, +2 haste
      | { kind: 'flatSaveDelta';  ability: AbilityScore; value: number } // -2 slowed DEX saves
      | { kind: 'flag' }                                     // manual rule, show note only
Effects WITHOUT `mechanic` (or with `kind:'flag'`) are display-only flags.

`Character` shape is UNCHANGED for status conditions — keep storing them in
`conditionIds: ActiveCondition[]` as `{ conditionId }`. Do NOT migrate buffs out of
`activeBuffSpells`; that path already works for AC/attack riders.

NEW data file: `src/renderer/src/shared/data/conditionsData.ts`
    export const CONDITIONS: Condition[]
    export const CONDITION_BY_ID: Record<string, Condition>
Cover, at minimum, the 16 already in the panel PLUS the user's examples that are
real conditions/terrain states (not spells): difficult-terrain, silence, slowed,
fly, haste. (bless / guidance / green-flame-blade / aid are SPELLS — they stay in
the `activeBuffSpells`/spell path; see "Buffs" below.)

Registry content (id -> category, mechanic, RAW note). `mechanic` shown only where
truly computable on a sheet:
  - blinded        debuff  flag   "Auto-fail sight checks; attacks vs you have ADV, your attacks DIS."
  - charmed        debuff  flag   "Can't attack the charmer; charmer has ADV on social checks."
  - concentration  neutral flag   "Tracks an active concentration spell (see spell panel)."
  - deafened       debuff  flag   "Auto-fail hearing checks."
  - exhaustion     debuff  flag   "Level-based penalties (DIS checks at 1, half speed at 2, ...)."
  - frightened     debuff  flag   "DIS on checks/attacks while source is in sight; can't move closer."
  - grappled       debuff  speedMultiplier:0  "Speed 0."
  - incapacitated  debuff  flag   "No actions or reactions."
  - invisible      buff    flag   "Attacks vs you DIS; your attacks ADV; heavily obscured."
  - paralyzed      debuff  speedMultiplier:0 + flag "Incapacitated; auto-fail STR/DEX saves; hits within 5ft are crits."
  - petrified      debuff  speedMultiplier:0 + flag "Incapacitated; resistance to all damage; auto-fail STR/DEX saves."
  - poisoned       debuff  flag   "DIS on attack rolls and ability checks."
  - prone          debuff  flag   "DIS on attacks; melee vs you ADV, ranged vs you DIS; half movement to stand."
  - restrained     debuff  speedMultiplier:0 + flag "Speed 0; attacks vs you ADV, yours DIS; DIS on DEX saves."
  - stunned        debuff  speedMultiplier:0 + flag "Incapacitated; auto-fail STR/DEX saves; attacks vs you ADV."
  - unconscious    debuff  speedMultiplier:0 + flag "Incapacitated, prone, drop everything; hits within 5ft crit."
  - difficult-terrain debuff speedMultiplier:0.5 "Each foot costs 2 — effective speed halved."
  - silence        debuff  flag   "Can't cast spells with a Verbal (V) component."
  - slowed         debuff  acDelta:-2 + flatSaveDelta(dex,-2) + speedMultiplier:0.5 + flag
                                  "Half speed; -2 AC & DEX saves; no reactions; max one attack/turn."
  - fly            buff    flag   "Gain a flying speed (e.g. 60 ft)."
  - haste          buff    acDelta:+2 + flag "Speed doubled; +2 AC; ADV on DEX saves; one extra limited action."
(Keep prose in `effects[].description`; `category` per row. RAW source: PHB
Appendix A conditions; Haste/Slow spells PHB.)

## Architecture & Placement
- Pure data: NEW `shared/data/conditionsData.ts` (no logic).
- Pure aggregation helper (NEW, belongs in `domain/rules/index.ts` because it is a
  pure function over `Character` + the registry):
      computeConditionModifiers(character): {
        acDelta: number
        speedMultiplier: number            // product of all multipliers, clamp >=0
        saveDeltas: Partial<Record<AbilityScore, number>>
        flags: { conditionId: string; note: string }[]
      }
  It iterates `character.conditionIds`, looks up `CONDITION_BY_ID`, and folds each
  `effect.mechanic`. No React/store/IO.
- AC: fold `acDelta` inside `computeACFull` (charCalculations.ts) — add the delta to
  the final AC. (This keeps ALL AC math in one place; `computeACFull` already
  consumes `activeBuffSpells` for `setsBaseAC`, so conditions join it there.)
- Speed: fold `speedMultiplier` inside `computeSpeedFull` (charCalculations.ts):
  `Math.floor(base * multiplier)` AFTER existing bonuses.
- Saves: in `AbilitiesPanel.tsx` where the per-ability save `bonus` is assembled,
  add `saveDeltas[ab] ?? 0` and surface a small badge ("-2 slowed") like the
  existing `equipBadge`/`auraMod` badges. (Bless's +1d4-to-saves is dice, not flat —
  do NOT fold into the number; surface it as a note, mirroring how attack-buff dice
  are already shown as separate rows.)
- Attack/ability-check dice riders (bless/guidance) are NOT status conditions; leave
  them on the spell-buff path and surface them as notes in the relevant detail
  panel, exactly like the existing `attackBuff` rows in `ActionDetailPanel.tsx`.
- UI: `features/conditions/ConditionsPanel.tsx` is rewritten to drive its chip list
  and active tags from `CONDITIONS` (category color: buff=success, debuff=danger,
  neutral=muted), and to render each active condition's effect note + flags. The
  store action stays `update({ conditionIds })`. No rules math in the component.
- Persistence: `conditionIds` already round-trips through `storageAdapter` on both
  platforms; no new persisted field.

## Solution Logic (data flow)
1. User toggles a chip -> `ConditionsPanel.toggle(id)` -> `update({ conditionIds })`
   (store action `updateCharacter`).
2. Derived stats recompute: `computeACFull` and `computeSpeedFull` now call
   `computeConditionModifiers` and apply `acDelta` / `speedMultiplier`.
   NOTE: `armorClass` is a PERSISTED snapshot (see VitalsPanel/AbilitiesPanel which
   call `computeACFull` on relevant edits). So ConditionsPanel.toggle MUST also
   recompute and persist `armorClass` when a condition with `acDelta` flips — mirror
   the existing `toggleBuff` which already does
   `update({ ..., armorClass: computeACFull({ ...char, ... }) })`.
3. `AbilitiesPanel` reads `computeConditionModifiers(char).saveDeltas` and adds the
   delta + badge per save row.
4. Flags (`kind:'flag'` and any `note`) render as read-only chips in the panel.

## Pseudocode
  function computeConditionModifiers(character):
    acc = { acDelta:0, speedMultiplier:1, saveDeltas:{}, flags:[] }
    for entry in character.conditionIds:
      cond = CONDITION_BY_ID[entry.conditionId]; if not cond: continue
      for eff in cond.effects:
        m = eff.mechanic
        if not m or m.kind == 'flag':
          acc.flags.push({ conditionId: cond.id, note: eff.description })
        else if m.kind == 'acDelta':         acc.acDelta += m.value
        else if m.kind == 'speedMultiplier': acc.speedMultiplier *= m.value
        else if m.kind == 'flatSaveDelta':   acc.saveDeltas[m.ability] = (acc.saveDeltas[m.ability] ?? 0) + m.value
    acc.speedMultiplier = max(0, acc.speedMultiplier)
    return acc

  // inside computeACFull(char): ...existing... ; return finalAC + computeConditionModifiers(char).acDelta
  // inside computeSpeedFull(char): return floor((base + bonuses) * computeConditionModifiers(char).speedMultiplier)
  // inside AbilitiesPanel save row: bonus += (mods.saveDeltas[ab] ?? 0)

## Edge Cases
- Legacy saves: `conditionIds` entries whose id is NOT in `CONDITION_BY_ID` (e.g.
  old free-text) -> skip in modifiers, still render as a plain tag (don't crash).
- Multiple speed multipliers (slowed + difficult-terrain) multiply (0.5*0.5=0.25);
  clamp >= 0; floor result; speed-0 conditions (grappled/restrained/stunned) win via
  multiplier 0.
- `acDelta` interaction with persisted `armorClass`: every code path that persists
  `armorClass` (ability edit in AbilitiesPanel, equip changes, `toggleBuff`,
  condition toggle) must call `computeACFull` so the snapshot stays correct; removing
  the condition must restore AC. (Add the same recompute to ConditionsPanel.toggle.)
- Haste's "extra action" and fly's "flying speed value" are NOT auto-computed —
  flag-only (no combat/movement engine). State this; do not fake an action economy.
- Concentration condition is neutral/no-op; don't double-count with
  `concentrationSpellId`.
- Cross-platform: pure functions only; identical on Electron/Capacitor.

## Assumptions
- "Wire" means: compute the subset a static sheet CAN compute (flat AC delta,
  speed multiplier, flat save delta) and FLAG the rest with a player-readable RAW
  note — exactly the pattern the user's own examples imply with "(add flag)".
- Keep the storage split: status conditions in `conditionIds`, spell buffs in
  `activeBuffSpells`. Unifying them is out of scope (would force a migration of live
  buff state and risks breaking AC/attack riders).
- Bless/Guidance/etc. dice riders are shown as notes, never folded into a flat
  number (consistent with existing `attackBuff` handling).

## State, Persistence & Migration
- No NEW persisted Character field. `conditionIds` shape unchanged.
- `armorClass` snapshot semantics unchanged (still recomputed+persisted on edits);
  just gains a condition term.
- Therefore NO `CURRENT_SCHEMA_VERSION` bump is required for Deliverable A.
- Round-trips through `storageAdapter` unchanged on both platforms.

## Validation

  * `computeConditionModifiers`: slowed -> acDelta -2, dex saveDelta -2,

  * `computeACFull` drops by 2 with slowed active and restores on removal.
  * `computeSpeedFull`: base 30 + slowed -> 15; +difficult-terrain -> 7 (floor).
  * Unknown/legacy conditionId is ignored (no throw).
- Extend `rules.test.ts` if the helper lands in `domain/rules`.
- `npm run typecheck` passes.
- Manual: toggle Slowed -> AC -2 and speed halved in VitalsPanel/AbilitiesPanel,
  DEX save shows "-2"; toggle off -> restores.

DELIVERABLE B — "Add Feature" button linked to the existing FEATS list
================================================================================

## Problem Definition
- WHAT (user-facing): Today `features/features-panel/FeaturesPanel.tsx` only has
  "+ Add Feature", which appends a FREE-TEXT entry to `customFeatures`. Add a second
  affordance ("+ Add Feat") that lets the player pick a real feat from the existing
  `FEATS` registry (`shared/data/featsData.ts`), add its id to `char.feats[]`, show
  it in the features list, and wire its mechanical consequence (or an explicit flag
  for the manual part). This is independent of the ASI/level-up path, which already
  grants feats via `LevelUpModal`.
- INPUTS: `FEATS`/`FEAT_BY_ID`, `char.feats`, `char.abilityScores`,
  `char.spellIds`, `char.armorClass`, plus per-feat ability choices.
- OUTPUTS: `char.feats` gains an id; ability-bonus feats raise scores (already
  handled in AbilitiesPanel via `FEAT_BY_ID[...].abilityBonus`); flag feats set NEW
  boolean flags; spell-granting feats add ids to `char.spellIds`. UI shows the feat
  in the Features list with a FEAT badge and a remove control.
- CONSTRAINTS: offline-first; Electron+iOS; must not corrupt existing saves; do not
  duplicate a feat already present; respect attunement/economy rules only as flags
  (no combat engine).

## Data Model
- READ existing: `FeatDef { id, name, description, abilityBonus?, abilityChoice? }`.
- WRITE existing: `char.feats: string[]` (push id); `char.spellIds: string[]` (for
  spell-granting feats); ability scores via the SAME recompute AbilitiesPanel
  already does for `abilityBonus`.
- NEW persisted Character flag fields (booleans, default undefined==false) — add to
  `entities/character/types.ts`, mark **NEW**, justified by the user's "(add flag)":
    piercerCritExtraDie?: boolean        // Piercer: +1 die on a piercing crit
    crusherCritAdvantage?: boolean       // Crusher: crit bludgeon -> attacks vs target ADV
    spellSniperDoubleRange?: boolean     // Spell Sniper: double attack-spell range; ignore 1/2 & 3/4 cover
    mountedCombatantFlags?: boolean      // Mounted Combatant: the three mounted riders
  (Booleans, not enums — each surfaces as a player-facing flag/badge; combat math
  isn't simulated.)
- Feats that GRANT spells (Shadow Touched -> Invisibility + one illusion/necromancy
  1st-level; Fey Touched -> Misty Step + one; Spell Sniper -> one attack cantrip)
  add the chosen spell ids to `char.spellIds`. Reuse the existing spell-picker
  (`features/level-up/SpellSelectionStep.tsx`) in a constrained mode if a choice is
  required; otherwise add the fixed spell id directly.
- NO new CSV/JSON columns.

## Architecture & Placement
- UI: `FeaturesPanel.tsx` gets a second button "+ Add Feat" opening a searchable
  picker over `FEATS` (filter out feats already in `char.feats`). Selecting a feat
  calls a store action. Render added feats in the existing `features` list with the
  CLASS/RACE/CUSTOM badge extended to include a 'feat' source -> "FEAT" badge, and a
  remove "×" (like custom features) that also UNWINDS its side effects.
- State change: NEW store action in `app/store/characterSlice.ts`:
      addFeat(id: string, featId: string, opts?: { abilityChoice?: AbilityScore; spellIds?: string[] }): void
      removeFeat(id: string, featId: string): void
  `addFeat` is the single place that: dedupes into `char.feats`; applies
  `abilityBonus`/chosen `abilityChoice` to scores and RECOMPUTES `armorClass`,
  `initiative`, `hitPoints.max` (reuse the exact recompute block already in
  `AbilitiesPanel.commitEdit` / the ASI path in `characterSlice` around lines
  239/330); sets the relevant NEW flag; merges granted `spellIds`. `removeFeat`
  reverses score/flag/spell changes it can safely reverse (see Edge Cases).
- Rules wiring (pure, in `domain/rules/index.ts`, joining the existing
  `feats.includes('greatWeaponMaster'|'sharpshooter'|'archery'|'sentinel'|'warCaster')`
  blocks):
    * Piercer / Crusher: surface in `ActionDetailPanel` crit section as a note/row
      ("Piercer: +1 die on piercing crit"; "Crusher: crit -> target ADV") — these
      are crit-time riders, shown as flags next to the weapon, not folded into the
      static attack number.
    * Spell Sniper: when `spellSniperDoubleRange`, show doubled range + "ignores
      1/2 & 3/4 cover" note wherever an attack-roll spell's range is displayed
      (SpellsPanel/ActionDetailPanel); flag-only for cover.
    * Mounted Combatant: flag-only (three riders shown as a note on the feat card).
  Keep these as display/flag wiring — none require a flat numeric change to AC, save
  or attack TOTAL, so no change to `computeAttackBonus`/`computeACFull` numbers.
- Persistence/migration: NEW boolean flags need a `v10_to_v11` (see below).

## Solution Logic (data flow)
1. User clicks "+ Add Feat" in FeaturesPanel -> picker lists `FEATS` minus owned.
2. If the feat has `abilityChoice` or grants a chosen spell, prompt (reuse existing
   choice UI / `SpellSelectionStep` constrained); else proceed.
3. Picker -> `addFeat(char.id, featId, opts)` (store) ->
   - push featId (dedupe),
   - apply ability bonus/choice + recompute AC/initiative/maxHP,
   - set NEW flag for piercer/crusher/spellSniper/mountedCombatant,
   - append granted spell ids to `spellIds`.
4. FeaturesPanel re-renders feat in the list (FEAT badge). Existing consumers
   (`AbilitiesPanel` ability badges, `domain/rules` feat blocks, `ActionDetailPanel`
   crit notes) pick up the change because they already read `char.feats` / flags.
5. Remove "×" -> `removeFeat` unwinds.

## Pseudocode
  addFeat(charId, featId, opts):
    char = state[charId]; if char.feats.includes(featId): return
    def = FEAT_BY_ID[featId]; if not def: return
    feats = [...char.feats, featId]
    scores = applyAbility(char.abilityScores, def.abilityBonus, opts.abilityChoice)
    patch = { feats, abilityScores: scores }
    patch.armorClass  = computeACFull({ ...char, ...patch })
    patch.initiative  = computeInitiativeFull({ ...char, ...patch })
    patch.hitPoints   = recomputeMaxHp({ ...char, ...patch })   // same block as commitEdit
    if featId == 'piercer':           patch.piercerCritExtraDie = true
    if featId == 'crusher':           patch.crusherCritAdvantage = true
    if featId == 'spell-sniper':      patch.spellSniperDoubleRange = true
    if featId == 'mountedCombatant':  patch.mountedCombatantFlags = true
    if opts.spellIds:                 patch.spellIds = unique([...char.spellIds, ...opts.spellIds])
    updateCharacter(charId, patch)

  removeFeat(charId, featId):
    drop featId from feats; clear its NEW flag; subtract def.abilityBonus/choice and
    recompute AC/initiative/maxHP; (granted spells: see Edge Cases — keep unless
    safely attributable). updateCharacter(...)

## Edge Cases
- Feat already owned (from ASI or race freeFeat) -> picker hides it; `addFeat`
  no-ops on dedupe.
- `abilityChoice` feat added with no choice -> require a choice before commit
  (disable confirm), mirroring `LevelUpModal`.
- Spell-granting feat: if the chosen 1st-level spell is already in `spellIds`, don't
  duplicate. On removeFeat, DON'T blindly strip granted spells if they could also be
  class-known (risk of removing a legitimately learned spell); safest = leave
  granted spells on removal and note it, OR track them under a dedicated list — for
  v1, LEAVE them and document. (State this as an assumption.)
- maxHP recompute must NOT reduce `current` below 0 (reuse existing clamp from
  `AbilitiesPanel.commitEdit`).
- `tough` already handled separately in HP calc — adding it via this button must not
  double-apply; route HP through the SAME single computeMaxHP path.
- Legacy saves lacking the NEW flags read as undefined -> falsy -> safe.
- Cross-platform: only pure data + store; identical on both adapters.

## State, Persistence & Migration
- NEW persisted fields: `piercerCritExtraDie`, `crusherCritAdvantage`,
  `spellSniperDoubleRange`, `mountedCombatantFlags` (all optional booleans).
- Bump `CURRENT_SCHEMA_VERSION` 10 -> 11 in `domain/migrations/index.ts` and add

- Confirm round-trip through `storageAdapter` (Electron `{id}.json` + Capacitor
